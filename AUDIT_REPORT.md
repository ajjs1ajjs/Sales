## 1. Executive Summary

Sales — невеликий статичний застосунок React/PWA: показує пропозиції Steam, добірки PC Game Pass, фільтри, обране та історію. Окремий Node.js-скрипт отримує зовнішні дані та надсилає Telegram-сповіщення. Зберігання — JSON-файли та браузерний localStorage; серверної БД, облікових записів і власного HTTP API немає.

**Оцінка: 68/100 — потрібні заплановані покращення. Загальний ризик: високий. Упевненість: середня.** Оцінка характеризує перевірену робочу копію, а не сертифікує production. Найсерйозніші проблеми стосуються відмовостійкості даних і релізів; критичних вразливостей або фактичного витоку секретів не підтверджено.

**15 знахідок: P0 — 0; P1 — 4; P2 — 10; P3 — 1.** Дефекти відтворено без зовнішніх повідомлень і без запису даних на диск, або підтверджено конкретними шляхами виконання. Це не докази інцидентів у production.

Найважливіше:

1. **AUD-01:** після успішної HTTP-відповіді з порожнім Steam-каталогом старий каталог усе ж перезаписується порожнім, попри повідомлення «Keeping old data»; запис `deals.json` також не атомарний.
2. **AUD-02:** успішно надісланий Telegram-батч не має стійкого checkpoint. Помилка наступного батча перериває весь запуск до збереження даних та історії, створюючи умови для повторних повідомлень.
3. **AUD-03:** довгі повідомлення обрізаються посеред HTML/елементів, а постійна HTTP-помилка або відсутність Telegram-конфігурації може позначити ненадіслані елементи як надіслані.
4. **AUD-04:** PowerShell-реліз неправильно перевіряє `git diff --quiet` і не зупиняється на низці невдалих `git commit/push`; можливі зайві релізи або хибне повідомлення про успіх.
5. **AUD-06/AUD-11:** власний Service Worker має проблеми fallback/життєвого циклу кешування; критичні сценарії збирача, SW і релізів не покриті наявними тестами.

Залежності загалом сучасні та сумісні за перевіреними peer-діапазонами. Обов'язкове цільове оновлення — **Vitest та `@vitest/mocker` з 4.1.11 до виправленої 4.1.12 або новішої перевіреної версії тієї ж гілки**. `npm audit` знайшов 2 moderate dependency entries, що відображають дві advisory у mocker та залежний Vitest; high/critical — 0, у production dependencies — 0 відомих знахідок цього сканування. Немає підстав міняти React, Vite або переходити на SSR-фреймворк заради новизни.

**Висновок щодо БД:** залишити JSON для публічних знімків і localStorage для персональних налаштувань. Слід покращити валідацію, атомарність, стан доставки та відновлення. Міграція на PostgreSQL/MongoDB/Redis не виправдана наявними обсягами й функціями.

Почати з перевірок відмов на fixtures, захисту останнього коректного знімка та обліку доставки; далі виправити реліз і SW. Спростити супровід можна виділенням чистих функцій із великого збирача, спільним контрактом JSON та усуненням дублювання релізної логіки. Переписування всього застосунку не потрібне.

### Запуск, перевірки та публікація

- `npm run dev` — Vite для локальної роботи; `npm run preview` — перегляд збірки.
- `npm run fetch` — отримання даних **із записом JSON і потенційним надсиланням Telegram**; під час аудиту не запускався.
- `npm run build` — генерація `public/sitemap.xml`, `tsc -b`, Vite/PWA build у `dist/`. Під час аудиту не запускався через запис файлів.
- `npm run lint`, `npm test` — ESLint і Vitest/jsdom; фактично виконані, результати в розділі 13.
- CI та release використовують Ubuntu і Node 22. Release виключає `data/` із синхронізації, що доречно зберігає власність даних за scheduler.

Сайт потребує статичного HTTPS-хостингу й доступу до власного JSON. Steam, Microsoft та Telegram потрібні збирачу, а не клієнту. Дані пропозицій публічні; користувацький wishlist залишається у браузері. Токени не мають потрапляти до клієнтської збірки.

## 4. Детальні знахідки

### Дані та збирач

### AUD-01. Порожній результат стирає Steam-каталог; знімок пишеться неатомарно

**ID:** AUD-01. **Категорія:** БД / цілісність даних. **Пріоритет:** P1.

**Поточний стан:** `fetchSteamGames()` повертає масив; захист від відмови спрацьовує лише при rejected promise. Після формування даних виконується прямий `writeFile` на цільовий `deals.json`.

**Проблема:** HTTP 200 із порожнім/зміненим payload проходить як успіх і може прибрати весь каталог. Частковий семантичний збій пошуку також може опублікувати меншу вибірку. Переривання прямого запису залишає ризик пошкодженого локального JSON. Це не доводить, що пошкоджений файл уже опублікований scheduler-ом.

**Докази:** `scripts/fetch-deals.ts:339–343` пропускає невалідну search-сторінку; `:669–672` лише логує збереження старих даних; `:926–934` записує саме `steam: freshSteam`. На відміну від history (`:938–940`), deals не використовує temp+rename. Ізольований запуск реального `run()` із mock `fetchSteamGames → []` і старим каталогом з одного елемента дав `steamSaved: 0`, успішне завершення та два in-memory записи.

**Рекомендація:** розрізняти complete/partial/failed результат джерела; не підміняти останній валідний каталог порожнім після непідтвердженої зміни контракту. Порожній повний Steam Top Sellers-каталог має вимагати окремого підтвердження валідності. Зберігати source status, дату останнього успішного джерела та причину fallback. Записувати валідований JSON через унікальний temp-файл і rename.

**Заміна:** безумовний запис нового масиву → перевірений знімок із last-known-good fallback; JSON залишається.

**Обґрунтування:** це захищає існуючі дані без введення сервера або БД. Справжнє видалення товарів слід відрізняти від деградації API, а не назавжди заморожувати всі записи.

**Очікуваний результат:** зовнішня зміна формату не стирає каталог; неповний запуск видимий як degraded.

**Ризики:** надто суворий поріг може затримати законне оновлення; fallback повинен мати видиму давність. Temp+rename не створює транзакції на два файли або на Git push.

**Складність:** середня. **Залежності:** немає; тести AUD-11 виконувати разом із виправленням.

**Критерії готовності:** fixtures `200 {}`, порожній categories+search, invalid search, частковий Game Pass, переривання запису; останній коректний snapshot зберігається, degraded видно, дозволене валідне очищення має окремий тест.

**Упевненість:** висока щодо коду та відтворення; поведінка зовнішнього publisher не перевірена.

### AUD-02. Підтвердження Telegram не переживають частковий збій запуску

**ID:** AUD-02. **Категорія:** надійність / цілісність даних. **Пріоритет:** P1.

**Поточний стан:** після кожного батча `markSent` змінює тільки об'єкт у пам'яті. Будь-яка retryable-помилка перериває `run()` до фінальних записів.

**Проблема:** перший батч міг бути доставлений, а наступний — ні; наступний запуск знову бачить стару history і може повторити перший. Недоступність Telegram також блокує збереження успішно отриманого каталогу. Коментар про захист від повторів не відповідає стійкості реалізації.

**Докази:** `scripts/fetch-deals.ts:801–803`, `:822–852`, `:857–940`; `:848` кидає помилку, записи лише на `:934`, `:939`. У mock-сценарії «Steam discount — HTTP 200, потім free batch — HTTP 500» було 2 спроби відправки і **0 записів** стану.

**Рекомендація:** відокремити публікацію каталогу від доставки. Мати стабільний event ID, pending/delivered/failed стан і стійко фіксувати результати завершених батчів. Для ephemeral CI гарантія має включати збереження стану між запусками, а не лише локальний temp-файл; контракт із зовнішнім scheduler треба перевірити окремо. Зберігати повернутий `message_id` для звіряння.

**Заміна:** лише in-memory `markNotified` → явний журнал стану доставки у чинному persistence-контурі.

**Обґрунтування:** невеликий обсяг дозволяє реалізувати це у версіонованому JSON; брокер або нова БД не потрібні. Telegram sendMessage не дає універсальної exactly-once гарантії: crash між доставкою та checkpoint потребує явної політики повтору/звіряння.

**Очікуваний результат:** відмова одного батча не скасовує облік попередніх та оновлення каталогу.

**Ризики:** необхідно визначити допустимість повтору при невідомому результаті; проста перестановка фінального `writeFile` не закриває всі crash windows.

**Складність:** середня. **Залежності:** AUD-01, контракт persistence зі scheduler; тести AUD-11.

### AUD-04. Локальний PowerShell-реліз не контролює результат Git коректно

**ID:** AUD-04. **Категорія:** DevOps. **Пріоритет:** P1.

**Поточний стан:** умови `if (git diff --cached --quiet)` використовують вивід команди. Після низки native Git-команд немає перевірки `$LASTEXITCODE`; встановлено лише `$ErrorActionPreference='Stop'`.

**Проблема:** quiet diff без змін повертає код 0 і порожній stdout, який PowerShell трактує як false. Шлях no-op не спрацьовує; аналогічно фінальний version-no-op. У Windows PowerShell 5.1 ненульовий native exit сам по собі не забезпечує потрібного stop. Невдалий push може супроводжуватися подальшими тегами/версією та повідомленням успіху.

**Докази:** `scripts/Release-Local.ps1:98–108`, `:140–146`; відсутні exit checks після `:107–108`, `:141–145`. Read-only перевірка в цій PowerShell 5.1 дала `git diff --cached --quiet: exit=0, stdout=null, [bool]stdout=false`. Повний release не запускався.

**Рекомендація:** запускати diff окремо й одразу перевіряти `$LASTEXITCODE`: 0 — no changes, 1 — changes, >1 — error. Для кожної commit/push/release-команди зупинятися на помилці; використовувати єдиний checked-native helper. Валідувати version як semver до будь-якого запису; передавати її в Node через env/argument, не вбудовувати у JavaScript-код (`:141`).

**Заміна:** stdout-based branching та unchecked native commands → exit-code-based release state machine.

**Обґрунтування:** виправляє наявний шлях публікації, не змінюючи hosting.

**Очікуваний результат:** no-op не створює тегів/комітів; помилка publish не повідомляється як успіх.

**Ризики:** скрипт може тепер зупинятися там, де раніше мовчки йшов далі; це слід перевірити на локальних fixtures/mocks без справжнього release.

**Складність:** середня. **Залежності:** узгодити provenance з AUD-13.

**Критерії готовності:** no diff, real diff, diff error, commit failure, rejected push, existing tag, invalid version; жодної наступної стадії після помилки, жодних зовнішніх записів у тестах.

**Упевненість:** висока. README називає Ubuntu основною платформою, але скрипт присутній і явно призначений для релізу, тому його дефект не можна ігнорувати; якщо цей шлях офіційно не потрібен, видалення його після рішення власника є простішою альтернативою.

### AUD-13. Версія, тег і build не мають надійного зв'язку із source commit

**ID:** AUD-13. **Категорія:** DevOps / документація. **Пріоритет:** P2.

**Поточний стан:** release спочатку публікує build у спільну artifact-гілку, потім створює release без явного target SHA, після цього змінює тільки source `package.json`. Існуючий tag може бути мовчки прийнятий для іншого build.

**Проблема:** при паралельному коміті scheduler між push і tag release може посилатися на інший tip спільної гілки. Немає явного source SHA/build provenance для відтворення. Версії вже розійшлися: manifest 0.1.3, lock/root 0.1.2. Це metadata drift; саме по собі не доводить, що npm ci не працює.

**Докази:** `.github/workflows/release.yml:98–111`, `:125–136`, `:139–152`; `scripts/Release-Local.ps1:115–145`; `package.json:4`, `package-lock.json:3,9`. Workflow може запускатися на вибраному ref; guard main та плану reconciliation source push у файлі немає. Cross-repo scheduler concurrency не перевірена.

**Рекомендація:** фіксувати source SHA, artifact commit SHA, version та timestamp у release metadata; tag прив'язувати саме до опублікованого artifact SHA. Не перевикористовувати release version для іншого build. Синхронно оновлювати package.json/lock; валідувати semver і дозволені refs. Визначити retry/reconcile, якщо artifact publish успішний, а source bump або tag — ні. Зберегти no-op за порівнянням build content.

**Заміна:** tag поточного remote tip + частковий version bump → SHA-bound release manifest та узгоджений bump.

**Обґрунтування:** shared artifact repo можна залишити; потрібна простежуваність та безпечне повторення частково виконаного релізу.

**Очікуваний результат:** кожну публікацію можна зіставити з кодом і відкотити shell без відкату свіжих даних.

**Ризики:** branch protection та права source push можуть потребувати окремого version PR; не обходити захист. Старі теги можуть не мати достатньої інформації для ретроспективного відновлення.

**Складність:** середня. **Залежності:** AUD-04; узгодження зі зовнішнім artifact publisher.

**Критерії готовності:** source SHA→build→artifact SHA→tag відновлюється однозначно; паралельний data commit не змінює target; existing version з іншим content відхиляється; повтор після partial failure безпечний; lock metadata збігається.

**Упевненість:** висока щодо конфігурації та drift; фактичну гонку в remote не відтворювали.

## 5. Аудит БД і зберігання даних

### Вибір сховища

**Залишити чинні JSON-знімки, оптимізувати їхню цілісність. Міграція на іншу БД не виправдана.** Дані читаються як невеликий публічний каталог; немає покупок, платежів, акаунтів, міжкористувацьких транзакцій або серверних довільних запитів. Вбудований full-text search, connection pool, SQL-індекси, ORM та міграції SQL тут не застосовуються.

Фактичний `public/data/deals.json`: **53 210 байтів**, `lastUpdated=2026-10-20T10:09:43.984Z`, 12 Steam і 45 Game Pass записів. Вбудована й окрема history мають по 87 записів та однаковий JSON-вміст на момент перевірки. Steam ID у цьому snapshot унікальні, валюта UAH; перевірка від'ємних цін і percent поза 0–100 дала 0. Це локальний snapshot приблизно триденної давності, не підтвердження застарілості live-сайту.

### Модель, ключі та інваріанти

- Steam ID та Microsoft BigId використовуються як природні ключі; `Map`/`Set` у збирачі дедуплікують джерела. Для майбутнього shared-контракту бажаний явний platform+ID; актуальні ID різного формату, підтвердженої колізії немає.
- History — словник `steam_free_*`, `steam_discount_*`, `gamepass_*`, `gamepass_popular_*`. Це фактично остання подія/стан cooldown на ключ, **не append-only журнал усіх подій**: повтор перезаписує entry, retention видаляє старі.
- Retention 30 днів для Steam і 120 для Game Pass; UI відсікає history старшу 30 днів. Це обґрунтована різниця між дедуплікацією та відображенням, але detected/baseline/delivered зараз змішані, див. AUD-02/AUD-03/AUD-05.
- Дати створюються через UTC `toISOString`, відображення явно використовує Europe/Kyiv. Це залишити. Дату `lastUpdated` і майбутні timestamps слід валідувати разом із контрактом.
- Ціни переводяться з minor units у JS number. Для UI без фінансових розрахунків цього достатньо; для порівняння змін краще minor units або визначене округлення. Проблема невідомої ціни — AUD-08, а не потреба іншої БД.
- Вибірки зараз обмежені Steam search pages і Game Pass lists; клієнтські filter/sort при таких обсягах доречні. Підтверджених N+1 SQL-запитів або повільних DB-планів немає, оскільки SQL не використовується.

### Запис, конкурентність, міграції та recovery

`notified-history.json` пишеться через один фіксований `.tmp`, потім rename; це позитивний крок, але не транзакція з `deals.json`, Git commit, push або Telegram. `deals.json` пишеться напряму. Немає локального single-writer lock; два одночасні ручні запуски можуть прочитати ту саму history, надіслати дублікати та конфліктувати за `.tmp`. Реальна concurrency зовнішнього scheduler невідома. Потрібні single-writer або явна optimistic-concurrency перевірка, унікальні temp paths, generation ID і правило відновлення authoritative history.

`coerceOldData` перевіряє лише форму масивів; при пошкодженому локальному файлі логування не переходить до remote recovery, а продовжує з порожнім default. Для history це може скинути cooldown. Політика має бути явною: пошкоджений state не є свідченням «раніше повідомлень не було»; зупинити доставку або відновити validated last-known-good.

Повноцінної `schemaVersion`/міграційної історії JSON немає; є сумісність `xbox_new → gamepass`, optional gamepass та ігнорування старого Epic. Додати малий versioned adapter, не ORM. Перед зміною: зберегти оригінальний snapshot/history; прогнати адаптер офлайн; порівняти ID, counts, ціни та timestamps; перевірити старий клієнт; випустити backward-compatible reader перед writer. Для rollback залишити reader, що розуміє попередню схему, і попередній валідний знімок. Без масового replay Telegram.

У поточному репозиторії не виявлено перевіреної процедури backup/restore або RPO/RTO. Git-історія artifact repo може допомогти, але вона зовнішня і не верифікована. Потрібні фактичні права, retention, sample restore та рішення, чи відновлювати знімок окремо від delivery state. Відкат shell не повинен відкочувати нові scheduler-дані.

Дані не синхронізуються між пристроями, не мають гарантованого backup і можуть бути очищені браузером — документувати як властивість локального wishlist. ## 7. Що залишити без змін

- **Статичний CSR/PWA і GitHub Pages.** Для каталогу без акаунтів і транзакцій немає доведеної потреби в SSR чи серверному runtime. HashRouter доречно обходить вимогу rewrite routes на Pages; індексація окремих hash-сторінок не обіцяється.
- **React 19, TypeScript, Vite, npm lockfile.** Наявні peer ranges сумісні, lint/tsc/tests проходять; точкове обслуговування краще за переписування.
- **JSON для каталогу та localStorage для wishlist.** Вартість і складність мінімальні; виправити гарантії запису, не технологію.
- **Lazy sections і history, ShowMore, debounce, мемоізовані вибірки.** Це адекватні обсягам оптимізації; немає доказу потреби у virtualization або global state library.
- **LocaleContext із двома локалями, shared price/date helpers.** Існуючий обсяг не вимагає великої i18n-платформи; `<html lang>` синхронізується.
- **Безпекові основи:** React text escaping, `safeUrl` відкидає небезпечні схеми, store links мають `noopener noreferrer`, Telegram HTML проходить escaping, немає виявленого `dangerouslySetInnerHTML` у runtime-коді. Не підміняти ці перевірки довірою до upstream.
- **CI:** SHA-pinned checkout/setup-node, `contents:read` для checks, npm ci, audit/lint/tests/build, timeout і concurrency; ручний release замість зайвих автоматичних публікацій.
- **Release preservation `data/`.** Дані scheduler не слід затирати локальним build snapshot.
- **Структуровані pino-логи, runId, backoff, rate limiter, cool-down та anti-spam caps.** Ці механізми корисні; виправити повноту timeout і стійкість delivery state.

## 8. Що можна спростити або прибрати

1. **Виділити збирач без зміни архітектурного класу.** Зараз один файл виконує API адаптацію, HTML parsing, planning, Telegram formatting, delivery і persistence. Невеликі модулі `sources`, `contract`, `plan`, `delivery`, `snapshot` плюс CLI entrypoint дозволять тестувати реальний код; не вводити універсальний plugin framework або десятки інтерфейсів.
2. **Прибрати дублікати алгоритмів із audit-тестів.** Зараз finite/coerce/token-string тести можуть проходити незалежно від production-коду. Після extraction імпортувати функції; це менше тестового коду з сильнішим доказом.
3. **Визначити один власник release logic.** Два окремі сценарії вже мають відмінності. Якщо локальний PowerShell-процес не потрібен, залишити manual Actions release й документований preview. Якщо потрібен — спільна checked логіка для версій/provenance та tests. Під час аудиту нічого не видалено.
4. **Розглянути видалення `@types/pino`.** Pino 10 уже містить типи; після видалення має пройти node tsc. Це невелике прибирання залежності, не безпековий emergency. `patches/README.md` уже описує відсутність активних patches; заголовок про застосування patch-package слід уточнити, а не повертати patch-package.
5. **Об'єднати контракт і selectors.** Зараз producer, consumer і tests мають незалежну coercion, а counts/render — різні predicates. Спільні невеликі функції зменшать drift без нової state-management бібліотеки.
6. **Не додавати infrastructure для вигаданого масштабу.** Клієнт читає приблизно 52 KiB JSON; HTTP cache та статичний CDN достатні. Кеш серверних запитів, Redis і broker не мають доведеної економічної користі.

Немає даних про фактичні тарифи, трафік і витрати Actions, тому суми економії не оцінювалися.

## 9. Цільова архітектура

Зберегти **один статичний React/PWA frontend та один невеликий scheduled collector**.

Collector адаптує два зовнішні джерела у versioned контракт із platform/ID, цінами та source status. Кожне джерело має lastSuccessfulAt і відокремлений error/degraded статус. Перевірений snapshot публікується незалежно від Telegram, атомарно на рівні файлу, із generation/source metadata та last-known-good fallback. Кількість items/drop reasons контролюється; зміна HTML Steam — contract failure, а не коректне очищення каталогу.

Notification planner — чиста функція над поточним каталогом та попереднім delivery state. Telegram adapter формує цілі валідні повідомлення, враховує length/rate limits і повертає delivery receipt. Journal розрізняє baseline/detected/pending/delivered/failed, переживає restart у чинному scheduler persistence. Не обіцяти exactly-once; визначити replay/reconciliation для невідомого результату. Один writer на generation або перевірювана optimistic concurrency.

Frontend читає той самий JSON, перевіряє контракт, зберігає останні дані під час refresh, оновлюється на foreground/online із TTL, показує stale/degraded та дату джерела. Shared selectors гарантують відповідність лічильників карткам. Wishlist залишається локальним. SW захищає immutable shell окремо від обмеженого runtime cache, підтримує 5xx/network fallback, зрозумілий update lifecycle та browser regression checks.

CI перевіряє app/collector/SW types, реальні parser/planner/delivery сценарії, JSON fixtures та невеликий offline/update E2E набір. Release прив'язує source commit, artifact commit і version; shell rollback не відкочує scheduler-дані. Зовнішній publisher/scheduler залишається за межею цього репозиторію, його concurrency та persistence треба підтвердити у власника.

### Моніторинг і межі безпеки

У цьому репозиторії є структуровані логи, але немає підтверджених SLO/alert правил. Достатньо почати з freshness за джерелами, run duration/exit, counts/invalid entries, HTTP status/timeouts/retries, delivered/failed/pending та віку черги. Для Pages — доступність JSON/shell і перевірка свіжості. Не потрібні Kubernetes чи Prometheus-кластер без реальної потреби; використати наявні можливості CI/hosting.

У коді не виявлено власних SQL/SSRF endpoints, серверних сесій, upload або admin API: SQL injection, server-side CSRF/RBAC/rate limiting не застосовуються до неіснуючих компонентів. `safeUrl` є перевіркою схеми, а не trusted-host allowlist; stricter store/image hosts можна додати в data contract як захист від підміни джерела, не називаючи поточне `http(s)`-посилання підтвердженим XSS.

`index.html:8` містить CSP із self script/connect, `object-src 'none'`, `base-uri 'self'`, `form-action 'none'`, upgrade-insecure-requests. Це позитивно. Meta CSP не замінює всі HTTP headers; налаштування HSTS, frame-ancestors, Referrer-Policy, Permissions-Policy, CDN та реального TLS не перевірено. `style-src unsafe-inline` відповідає наявним inline styles; звужувати лише після інвентаризації, не ламати UI механічно.

У поточних файлах патерн-пошук поширених PAT/Bot/private-key форматів не знайшов секретів; це не повний secret scan Git history. У release `:98` токен інтерполюється у clone URL, що також зберігається у remote config та передається процесу. Це можливість посилення, без доказу витоку: перейти на credential helper/налаштований checkout без credential-bearing URL, обмежити токен потрібним artifact repo та мінімальними permissions замість широкої поради `repo` у README. Логи й артефакти не повинні містити remote credentials. Secrets values не читалися й не включені до звіту.

## 12. Реалізація та перевірка виправлень

Follow-up 23.10.2026 вніс такі зміни після аудиту:

- **AUD-01:** Steam використовує останній справний знімок, якщо запит завершився помилкою або повернув порожній список за наявності попередніх записів. `deals.json` та історія пишуться через унікальний тимчасовий файл і атомарну заміну.
- **AUD-02–03:** Telegram ділить повідомлення за довжиною й кількістю елементів без обрізання HTML; підтверджені партії одразу зберігаються в історію. Відсутні credentials та помилки доставки залишають елементи непідтвердженими для наступного запуску.
- **AUD-04:** локальний PowerShell release розрізняє exit code `git diff --cached --quiet`, перевіряє результати commit/push та синхронно оновлює версії в `package.json` і `package-lock.json`.
- **AUD-05/AUD-08/AUD-10:** Game Pass popular-only записи не оголошуються новинками; Steam popular-фільтр зберігає discounted popular ігри; відсутня/некоректна ціна Steam відкидається замість хибного безкоштовного запису.
- **AUD-07/AUD-09:** тайм-аут охоплює читання body; клієнтська схема відкидає некоректні записи, а довгоживучий провайдер повторно завантажує дані за розкладом, після повернення вкладки та після відновлення мережі, зберігаючи попередній результат при збої.
- **AUD-06/11:** shell precache відокремлено від обмеженого runtime cache; data/navigation використовують network-first з fallback на cache, а записи в кеш очікуються до завершення відповіді. Strategy тести викликають ті самі production-функції та перевіряють precache/cleanup, offline/503 fallback, cache writes/eviction. `tsconfig.sw.json` перевіряє worker у build; CI більше не пропускає data-only зміни. Додані PowerShell release-state tests перевіряють no-op, dirty state й помилки commit/push.
- **AUD-12:** Vitest оновлено до 4.1.12; `npm audit --audit-level=moderate` не знайшов вразливостей на момент перевірки.
- **AUD-13:** release manifest містить версію, source SHA, artifact SHA та UTC timestamp; release tag створюється на точному artifact commit, а manifest додається asset-ом. Повторне використання tag перевіряє provenance, неузгоджену версію відхиляє. Якщо збій стається після artifact push, після tag creation або до source bump, повторний запуск знаходить marker у release/commit і продовжує; version bump оновлює package та lockfile й не перезаписує новіші зміни `main`.
- **AUD-14:** мінімум Node задокументовано та перевіряється як 22.13+ у package metadata та installer.
- **AUD-15:** додано `prefers-reduced-motion: reduce` для анімацій, переходів і плавного прокручування.

Додано регресійні тести для Steam fallback/цін, Game Pass classification, Telegram limits, атомарного JSON, body timeout, SW strategies та release state/provenance. Перевірка follow-up: **82 тести / 19 файлів пройшли**, PowerShell 5.1 release tests пройшли, lint і production build пройшли (включно з окремим SW typecheck), `npm audit --audit-level=moderate` — 0 вразливостей. У preview production bundle сторінка завантажилася, а SW активувався та контролював клієнт; offline та HTTP error fallback підтверджені тестами strategy-функцій.

Початкові CSS-зміни користувача в чотирьох файлах не входили до цього follow-up.
